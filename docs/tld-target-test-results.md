## The one real bug — fixed

23 gTLDs (e.g. `.cat`, `.barcelona`, `.sap`, `.aco`, `.seat`) whose registry RDAP servers **reject a plain `Accept: application/json` with HTTP 406**. Per RFC 7480 §4.2 RDAP serves `application/rdap+json`; recon now sends `Accept: application/rdap+json, application/json` for all RDAP requests. Verified live (406 → 200) and locked with an offline test (suite 125 → 126 green). Fixed TLDs:

## Broken — bootstrap-delegated but the endpoint responds unusably (12); first-class `broken` state (v0.6.0)

These TLDs are **delegated in the IANA RDAP bootstrap** (a public RDAP server demonstrably exists) and the endpoint **answered** — but with a response we cannot use: an untrusted/self-signed TLS certificate, or an HTTP error status (4xx / 5xx). As of **v0.6.0** recon classifies this as a distinct fourth state — **`{"supported": true, "rdap_source": "broken", "cause": "<slug>", "http_status": <int|null>, "retryable": <bool>, "reason": …}`** — rather than the bare exit-2 error it previously surfaced. This is the honest signal: *the endpoint is faulty — skip the field; `retryable` tells you whether a later attempt can help.* It is **not** `unsupported` (a server exists) and **not** `unreachable` (we got an HTTP-layer response, not a transport reset).

recon still does **not** disable TLS verification or fake a fetch — the bad-cert faults remain genuine registry-side breakage; recon simply now *labels* them descriptively. `broken` is only emitted after **both** the authoritative server **and** the rdap.org redirector are exhausted, so it never fires where the redirector could still rescue the lookup. All 12 re-run one-at-a-time under the new build on 2026-07-28 (sequential, `--retries 0`) and emit the new state cleanly.

**Exit code by retryability:** non-retryable `broken` (bad-cert, HTTP 4xx) → **exit 4**; retryable `broken` (HTTP 5xx) → **exit 3** (same "retry later" tier as `unreachable`).

> **Boundary check (2026-07-28, v0.6.0):** the `broken` trigger is deliberately narrow and mutually-exclusive with `unreachable`. Verified live and in the offline truth-table that: a bad TLS cert → `broken/bad-cert` (exit 4), **not** `unreachable` (a cert-verification failure is a distinct `ssl.SSLCertVerificationError`, not a transport reset); HTTP 4xx → `broken` non-retryable (exit 4); HTTP 5xx → `broken` retryable (exit 3); while a connection reset / TLS-RST / read timeout still → `unreachable` (exit 3), and a **429/ban, DNS-resolution failure, connection-refused, or genuine `unsupported` absence never land in `broken`**. Boundary spot-check also confirmed a PASS TLD (`google.com`) and a genuine-unsupported TLD (`nic.ae`) are unaffected (both exit 0).

## Note on the ARTIFACT cohort (333)

- Control domains that PASSed early in the sweep began failing once the limit was exhausted;
- Identity Digital returned `HTTP 429` with **`Retry-After: ~82000s` (~23 h)** — an explicit temporary ban;
- 145 of the initially-failed TLDs recovered to PASS as the window partially reset during re-probing;
- recon already honors `Retry-After`/`429` with backoff, so normal one-domain-at-a-time use never trips this.

These 333 TLDs construct the correct authoritative RDAP URL and are expected to PASS; they can be re-validated once the ~23 h backend cooldown expires. They are **not** counted as passing above because they were not independently re-confirmed this session.
